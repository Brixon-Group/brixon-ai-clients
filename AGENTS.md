# Maintaining this marketplace

This repository is public and installed by Brixon AI clients in Claude Code and Codex.

## Layout

| Path | Purpose |
|---|---|
| `.claude-plugin/marketplace.json` | Claude Code catalog |
| `.agents/plugins/marketplace.json` | Codex catalog, same plugins |
| `plugins/<name>/.claude-plugin/plugin.json` | Claude Code manifest; its `version` is authoritative |
| `plugins/<name>/.codex-plugin/plugin.json` | Codex manifest: same name, version and `mcpServers`, plus `skills` and `interface` |
| `plugins/<name>/skills/` | Skills, one folder each, `name` in the frontmatter equal to the folder |
| `plugins/brixon-ai-client-core/rules/CLIENT.md` | Working rules for clients' AI; the only copy of the rules text |
| `plugins/brixon-ai-client-core/hooks/hooks.json` | Claude Code: prints `rules/CLIENT.md` into context at every session start |
| `plugins/brixon-ai-client-core/skills/setup-rules/` | Codex (no plugin hooks): writes the rules as a marked block into the client's global `AGENTS.md` |
| `plugins/brixon-ai-client-core/cli/index.mjs`, `feedback/` | The bundled Brixon CLI and its provenance record. Generated by `scripts/sync-feedback.mjs`; never edit by hand |
| `plugins/brixon-ai-client-core/docs/setup.md` | Setup notes for a client's IT: Node.js, `config.json`, `doctor`, hosts to allow |
| `scripts/check.mjs` | Consistency and public-content check, run by CI on every pull request |
| `scripts/sync-feedback.mjs` | Builds the Brixon CLI into a plugin as one file with a provenance record |

## Rules

- Nothing internal: no local paths, internal repository or service names, customer data, keys or tokens. `scripts/check.mjs` catches the common cases; it is not a full review.
- MCP servers are plain `https` entries. Customers sign in through the browser (OAuth); never add headers, env values or keys.
- Add only MCP servers that clients can sign in to themselves. The CLI holds no sign-in of its own; a skill that needs a connection clients cannot have yet must say so.
- Rules in `rules/CLIENT.md` are generic: nothing about Brixon's own repositories, tools or team habits. Every session pays for them, so keep them short; Claude Code cuts hook output above 10,000 characters.
- Bump the version in the marketplace entry and both manifests together: major for removed features, minor for new ones, patch for fixes.
- Before a pull request: `node scripts/check.mjs` and `node --test 'scripts/*.test.mjs'`.

## Brixon CLI

The plugin ships the Brixon CLI (Feedback publishing and the shared `put` upload command) as one
bundled file. To update it, run from a clean, `npm ci`-installed checkout of the Feedback tool:

```
node scripts/sync-feedback.mjs /path/to/feedback-tool-checkout
```

This writes `cli/index.mjs` and `feedback/` (package.json, licence notices, `upstream.json` with
commit and hashes) into `plugins/brixon-ai-client-core/`. `--check` verifies an existing build, and
`FEEDBACK_TEST_SOURCE=<checkout> node --test scripts/sync-feedback.test.mjs` tests the build.
The sync, its test and the CLI itself need Node.js 24.14 or newer.

- Release only a build whose `upstream.json` commit is on the Feedback tool's main branch. A build
  from a work branch is for review; sync again from main before the version goes out.
- The Node.js requirement comes from the CLI itself (currently 24.14). Keep `docs/setup.md`, the
  README, the skills and `node-version` in `.github/workflows/check.yml` in line with it when it
  changes.
- Skills find the CLI as `../../cli/index.mjs` relative to their own folder. The CLI holds no
  credentials; uploads use a short-lived ticket from the MCP server that prepared them.
- After a sync, read the new help text and the default origins (`doctor` shows them) and update
  `docs/setup.md`: it lists the hosts a client's firewall must allow.
- Do not add an MCP server to the manifests before clients can sign in to it. The `brixon-feedback`
  and `brixon-upload` skills state that their connections come on activation by Brixon; change
  that wording together with the manifest entry.
- Clients get the client edition of the CLI: the sync builds it with `__BRIXON_CLI_EDITION__`
  set to `client`, lets the bundler drop the branches that depend on the edition, and records the
  edition in `upstream.json`. Code that is merely unused in this edition, such as the video
  module, stays in the file. The check runs the committed build
  and fails unless it reports itself as `Brixon CLI` and its help has no video options.
- Video pages are not part of the client offering; the skills do not describe them.
- The upload host of Image Generation is not a default of the client edition. Do not list it in
  `docs/setup.md` until it is final.
